# 현업 요청서 대응 (외부정보 센싱 NANO)

2026-10-16 정리. 이 프로젝트는 대외협력팀·커뮤니케이션팀 대상 "외부정보 센싱 NANO" 인력 투입 요청서를 보고
"이런 것이 필요할 것"이라고 추정해 선행 구축하는 것이다. 기술 플랫폼은 현업 쪽에서 아직 미결정이다.
요청서가 적은 기술 요건과 지금 상태, 그리고 그에 맞춰 바꾼 로드맵을 여기에 둔다.

## 두 팀이 실제로 하는 일

- **대외협력**: 부처·국회·공공기관·협회의 정책, 규제, 공고, 보도자료 동향. 놓치면 손해인 공고(입찰·지원 사업·규제 변경).
- **커뮤니케이션**: 자사·경쟁사·이슈가 언론에 어디서 어떻게 보도됐는지. 아침 클리핑과 윗선 보고.

둘 다 **사이트 단위가 아니라 키워드 단위**로 생각하고, **물어보는 것(챗봇)보다 받아 보는 것(알림·다이제스트)** 을 먼저 쓴다.
받아 보는 쪽은 일간 다이제스트(`/api/v1/digests`, M2, 2026-10-16)로 들어갔다: 매일 정한 시각에 감시별·토픽별로 묶은 보고를 메일 또는 웹훅으로.

## 안티봇 범위 합의안 (현업과 서면 합의용, 초안)

| 항목 | 이 시스템의 입장 | 대신 하는 것 |
| --- | --- | --- |
| robots.txt가 금지한 경로 | 수집하지 않는다 | 관리자에게 사유를 보여 준다 |
| CAPTCHA·봇 확인 화면 | 풀지 않는다. BLOCKED로 분류하고 멈춘다 | 같은 정보를 주는 공개 API·RSS를 찾는다 |
| IP 차단·요청 제한(429) | IP를 바꿔 가며 피하지 않는다. 즉시 멈추고 관리자 재점검으로만 재시도 | 도메인당 2초 이상 간격, 식별 가능한 User-Agent |
| 회사가 구독하는 유료·회원제 사이트 | **회사 계정으로 로그인해 수집할 수 있다** (합의 시). 계정은 관리자가 등록, 세션은 시스템이 유지 | 약관이 자동 수집을 금지하면 제외 |
| 공개 API 키 | 사람이 발급한다. 자동 가입·약관 동의 대행은 하지 않는다 | 발급 뒤 검증·암호화 보관·쿼터·만료 감시는 자동 |
| 언론 기사 본문 | 저장하지 않는다 (제목·링크·발행일) | 보도 모니터링은 뉴스 검색 API로. 본문 저장 범위는 법무 확인 뒤 조정 |

## 공개 API 우선 대상

| 제공처 | 용도 | 발급 | 비고 |
| --- | --- | --- | --- |
| 네이버 뉴스 검색 API | 키워드로 언론 보도 | 앱 등록 후 즉시 | **구현됨** (`apis/naver_news.py`, provider `naver_news`, 키 `client_id:client_secret`). 키워드 감시(`/api/v1/watches`)의 주 소스, 60분 주기, 제목·링크·발행일만. 일 한도 25,000 — 호출 수 로그(`SENSING_NAVER_DAILY_LIMIT`), 정확한 쿼터 추적은 후속 |
| DART 오픈API | 공시 | 회원가입 후 즉시 | 회사(corp_code)별 조회 |
| 공공데이터포털 | 부처·기관 데이터 | 활용 신청, 대부분 자동 승인 | 일부는 심의 |
| 정책브리핑 korea.kr RSS | 정부 보도자료 | 키 없음 | 이미 사이트맵으로 수집 가능 |
| 열린국회정보 API | 의안·회의록 | 가입 후 발급 | 대외협력용 |

발급은 관리자가 한 번씩 손으로 한다 (다섯 곳이면 한나절). 시스템은 카탈로그로 "이 도메인은 API로 받는다"를
판단하고, 키가 없으면 관리자 큐에 "API 키 발급 필요" 항목을 만들며, 키가 들어오면 시험 호출로 검증한 뒤 자동으로 진행한다.

## 공급사 리스크 소스 (2026-10-16, 케이던시아 병행 활용에 맞춰)

현업이 삼성SDS의 구매·공급망관리 SaaS 케이던시아(Caidentia)를 함께 쓴다. 고객(대외협력·커뮤니케이션)과 수집 엔진은
그대로 두고, **데이터 소스를 "거래처(공급사)에 무슨 일이 있었나"를 알 수 있는 쪽으로 넓힌다.** 뉴스·공시 위에 아래 공공 API를
더하면 회사 단위의 위험 신호가 잡힌다. 모두 공개 API이고 M2-1의 자격 증명·카탈로그 구조에 커넥터만 추가하면 된다.
전제는 **회사 마스터**(이름, 별칭, 사업자등록번호, DART 고유번호, 케이던시아 ID)다. 사업자번호와 고유번호가 있어야 아래 API를
회사별로 부를 수 있다.

| 소스 | 신호 | 키 | 비고 |
| --- | --- | --- | --- |
| 국세청 사업자등록 상태 조회 (공공데이터포털) | 휴업·폐업·과세유형 변경 | 공공데이터포털 서비스키 | **구현됨** (M3-1, 2026-10-16): 회사 마스터(`company`)의 사업자번호로 점검 소스(`kind CHECK`, 하루 1회)가 조회해 `company_signal` BIZ_STATUS(폐업·휴업 HIGH, 미등록 MEDIUM, 과세유형 변경 LOW)로 기록. 가장 확실한 "거래 가능 여부" 신호 |
| 조달청 부정당업자 제재 정보 (공공데이터포털) | 입찰 참가 제한·제재 기간 | 공공데이터포털 서비스키 | 회사명·사업자번호로 대조 |
| DART 기업개황·정기보고서 재무 | 감사의견, 자본잠식, 매출 급감, 최대주주 변경 | DART 키 (이미 등록) | corp_code 매핑은 기업개황(company.json)과 corpCode.xml로 |
| DART 공시 목록 (이미 구현) | 소송, 영업정지, 회생·파산 신청, 임원 변동 | DART 키 | 회사별(corp_code) 조회로 전환 |
| 네이버 뉴스 검색 (이미 구현) | 사고·리콜·수사·파업 보도 | 네이버 키 | 회사 별칭을 검색어로. 제목만 저장. **회사 연결 구현됨** (M3-1): 회사마다 감시 `회사:<이름>`이 생기고 걸린 기사는 `document_company`(WATCH), 보강 태그 정확 일치는 TAG, 사건·사고·인사·조직 토픽이면 `company_signal` NEWS(MEDIUM) |
| 공정거래위원회 의결·제재 | 과징금·시정명령 | 사이트 크롤링 또는 공공데이터포털 | API 유무 확인 필요 |
| 법원 공고 (회생·파산) | 회생·파산 개시 | 키 없음 | 크롤링 가능 여부 확인 필요 |

리스크 신호 분류는 지금의 토픽(정책·규제, 자사, 경쟁사…)과 별도로 **두 번째 체계**로 둔다: 재무 악화, 법적 제재·소송, 사고·리콜,
경영권·임원 변동, 영업 중단(휴·폐업·입찰 제한), 평판. 심각도(높음·중간·낮음)는 소스 종류로 기본값을 정하고 LLM 분류로 보정한다.

케이던시아 연동은 SDS에 두 가지를 확인한 뒤 정한다: 공급사 마스터를 내주는 API가 있는지, 외부 이벤트를 받는 API가 있는지.
있으면 마스터 동기화와 이벤트 전달, 없으면 다이제스트 웹훅과 CSV 내보내기로 시작한다. 공급사 목록은 민감 정보이므로
SaaS로 무엇이 나가도 되는지 보안 검토가 먼저다.

## 챗봇에서의 등록 흐름 (M4, DART 예)

1. "DART 수집해 줘" → `register_source` 도구 → 등록 함수가 중복·권한을 판정한다 (화면과 같은 코드).
2. 도메인이 API 카탈로그에 "API 전용"으로 있으면 크롤링을 시도하지 않고 "공시 API 키가 필요합니다"와 발급 링크를 답한다.
   관리자 큐에 "API 키 발급 필요: DART"가 생긴다.
3. 관리자·등록 담당자가 키를 입력한다 (`submit_api_key` 도구 또는 관리자 화면). 일반 사용자가 넣으면 "관리자에게 전달했습니다".
4. 시험 호출 → 암호화 보관 → 소스를 `API` 방식으로 설정 → 첫 수집 → 주기 수집.
   - 3·4단계는 이미 있는 `POST /api/v1/api-credentials`(백엔드 `ApiCredentialService.save`)로 이뤄진다: 암호화 저장 뒤 그 제공자의
     키를 기다리던 소스에 ONBOARD 작업을 넣고, 워커가 시험 호출·설정·첫 수집을 한다. `submit_api_key` 도구는 이 메서드를 그대로 부른다.
5. 키는 대화 본문에 남기지 않는다 (대화는 DB에 영구 보관되므로 받는 즉시 본문에서 지우고 자격 증명 테이블에만 둔다).
6. 등록 점검은 수십 초가 걸리므로 "등록했어요, 점검 중입니다"로 답하고 결과는 다음 턴·알림으로 준다.

LLM은 사용자 말을 도구 호출로 바꾸고 결과를 말로 풀 뿐이다. 등록·점검·키 검증·수집은 결정적 코드가 하므로
챗봇이 상태를 거짓으로 답할 여지가 없다.
