# 현업 요청서 대응 (외부정보 센싱 NANO)

2026-10-16 정리. 이 프로젝트는 대외협력팀·커뮤니케이션팀 대상 "외부정보 센싱 NANO" 인력 투입 요청서를 보고
"이런 것이 필요할 것"이라고 추정해 선행 구축하는 것이다. 기술 플랫폼은 현업 쪽에서 아직 미결정이다.
요청서가 적은 기술 요건과 지금 상태, 그리고 그에 맞춰 바꾼 로드맵을 여기에 둔다.

## 두 팀이 실제로 하는 일

- **대외협력**: 부처·국회·공공기관·협회의 정책, 규제, 공고, 보도자료 동향. 놓치면 손해인 공고(입찰·지원 사업·규제 변경).
- **커뮤니케이션**: 자사·경쟁사·이슈가 언론에 어디서 어떻게 보도됐는지. 아침 클리핑과 윗선 보고.

둘 다 **사이트 단위가 아니라 키워드 단위**로 생각하고, **물어보는 것(챗봇)보다 받아 보는 것(알림·다이제스트)** 을 먼저 쓴다.

## 요건 대응표

| 요청서 요건 | 현재 (M1 완료 기준) | 판정 | 계획 |
| --- | --- | --- | --- |
| 스케줄 수집, 중복 제거, 정형화·저장 | DB 작업 큐, URL 중복, 본문 해시 버전 | 맞음 | 같은 뉴스의 매체 간 중복 묶기는 M4 검색에서 |
| RSS 연동 | 자동 탐색 1단계 | 맞음 | |
| 공개 API(뉴스·공시) 연동 | 스키마에 `API` 방식만 있고 구현 없음 | **빠짐** | **M2**: API 카탈로그, 자격 증명 저장소, API 수집기 |
| 동적 페이지 | 없음 | 예정 | M3 Playwright |
| 로그인·세션 대응 | 로그인 페이지는 BLOCKED 처리 | **합의 필요** | 회사 계정 세션 모드는 아래 합의안 뒤에 |
| IP 차단·CAPTCHA 대응 | 우회하지 않음 (원칙) | **범위 명시** | 우회 대신 공개 API로 대체 |
| 한국어 전처리, 키워드 추출, 분류·요약 | 없음 | 예정 | **M2** 수집 시점 요약·분류 태그, M4 Kiwi·임베딩 |
| 프롬프트 설계, API 연계 요약 | LLM 인터페이스와 레시피 생성 프롬프트 | 일부 | M2 요약·분류 프롬프트, M4 챗봇 |
| RAG, Agent | 스키마(chunk·chat_*)와 `LlmClient` 자리 | 예정 | M4 |
| 컴플라이언스(robots·저작권·개인정보) | robots 준수, 언론사는 제목·링크만, AI 봇 차단 표시, 내부망 차단, 감사 로그 | 요청서보다 앞섬 | 저장 범위는 법무 확인 |

## 안티봇 범위 합의안 (현업과 서면 합의용, 초안)

| 항목 | 이 시스템의 입장 | 대신 하는 것 |
| --- | --- | --- |
| robots.txt가 금지한 경로 | 수집하지 않는다 | 관리자에게 사유를 보여 준다 |
| CAPTCHA·봇 확인 화면 | 풀지 않는다. BLOCKED로 분류하고 멈춘다 | 같은 정보를 주는 공개 API·RSS를 찾는다 |
| IP 차단·요청 제한(429) | IP를 바꿔 가며 피하지 않는다. 즉시 멈추고 관리자 재점검으로만 재시도 | 도메인당 2초 이상 간격, 식별 가능한 User-Agent |
| 회사가 구독하는 유료·회원제 사이트 | **회사 계정으로 로그인해 수집할 수 있다** (합의 시). 계정은 관리자가 등록, 세션은 시스템이 유지 | 약관이 자동 수집을 금지하면 제외 |
| 공개 API 키 | 사람이 발급한다. 자동 가입·약관 동의 대행은 하지 않는다 | 발급 뒤 검증·암호화 보관·쿼터·만료 감시는 자동 |
| 언론 기사 본문 | 저장하지 않는다 (제목·링크·발행일) | 보도 모니터링은 뉴스 검색 API로. 본문 저장 범위는 법무 확인 뒤 조정 |

## 공개 API 우선 대상

| 제공처 | 용도 | 발급 | 비고 |
| --- | --- | --- | --- |
| 네이버 뉴스 검색 API | 키워드로 언론 보도 | 앱 등록 후 즉시 | 일 한도 있음. 키워드 감시의 주 소스 |
| DART 오픈API | 공시 | 회원가입 후 즉시 | 회사(corp_code)별 조회 |
| 공공데이터포털 | 부처·기관 데이터 | 활용 신청, 대부분 자동 승인 | 일부는 심의 |
| 정책브리핑 korea.kr RSS | 정부 보도자료 | 키 없음 | 이미 사이트맵으로 수집 가능 |
| 열린국회정보 API | 의안·회의록 | 가입 후 발급 | 대외협력용 |

발급은 관리자가 한 번씩 손으로 한다 (다섯 곳이면 한나절). 시스템은 카탈로그로 "이 도메인은 API로 받는다"를
판단하고, 키가 없으면 관리자 큐에 "API 키 발급 필요" 항목을 만들며, 키가 들어오면 시험 호출로 검증한 뒤 자동으로 진행한다.

## 챗봇에서의 등록 흐름 (M4, DART 예)

1. "DART 수집해 줘" → `register_source` 도구 → 등록 함수가 중복·권한을 판정한다 (화면과 같은 코드).
2. 도메인이 API 카탈로그에 "API 전용"으로 있으면 크롤링을 시도하지 않고 "공시 API 키가 필요합니다"와 발급 링크를 답한다.
   관리자 큐에 "API 키 발급 필요: DART"가 생긴다.
3. 관리자·등록 담당자가 키를 입력한다 (`submit_api_key` 도구 또는 관리자 화면). 일반 사용자가 넣으면 "관리자에게 전달했습니다".
4. 시험 호출 → 암호화 보관 → 소스를 `API` 방식으로 설정 → 첫 수집 → 주기 수집.
5. 키는 대화 본문에 남기지 않는다 (대화는 DB에 영구 보관되므로 받는 즉시 본문에서 지우고 자격 증명 테이블에만 둔다).
6. 등록 점검은 수십 초가 걸리므로 "등록했어요, 점검 중입니다"로 답하고 결과는 다음 턴·알림으로 준다.

LLM은 사용자 말을 도구 호출로 바꾸고 결과를 말로 풀 뿐이다. 등록·점검·키 검증·수집은 결정적 코드가 하므로
챗봇이 상태를 거짓으로 답할 여지가 없다.
