# 사이트를 등록하면 기사를 어떻게 찾아 가져오나

2026-10-18 기준, 실제로 등록해 본 사이트(주간조선·연합뉴스·정책브리핑·뉴스스탠드·주간지 8곳)의 흔적으로 정리한 것이다.
핵심은 **LLM이 아니라 규칙**이다. LLM은 켜 두었을 때 "레시피 보조"와 "수집 뒤 요약·분류"에만 쓴다.

## 전체 흐름

```
URL 입력 → 도메인으로 정규화 → [워커] 사전 점검 → 입구 찾기 → 기사 패턴 만들기 → 샘플 품질 검사 → 설정 저장 → 첫 수집
                                                                                            ↓
                                                                   60분(언론사)·180분·360분(공공)마다 입구를 다시 열어 못 본 주소만 수집
```

사용자가 하는 일은 URL 입력뿐이다. 기사 주소를 넣어도 사이트(도메인) 단위로 등록된다. 판단이 안 되는 사이트는 사용자에게
되묻지 않고 **관리자 처리 대기 큐**로 보낸다.

## 1. 사전 점검 (PROBE)

- `robots.txt`를 읽는다. 전체 금지면 `ROBOTS_DISALLOWED`로 등록을 거절한다(네이버 뉴스·의안정보시스템이 이 경우).
  GPTBot·ClaudeBot 등 AI 봇만 막아 둔 사이트는 수집하되 `ai_restricted`로 표시해 챗봇 근거에서 뺄 수 있게 한다(주간조선·연합뉴스).
- 홈을 연다. 봇 확인 화면(Cloudflare·reCAPTCHA 등)·로그인 페이지·429면 **우회하지 않고** `BLOCKED`로 멈춘다(Congress.gov).
  홈이 403이면 사이트 단위 차단으로 본다. 추측해서 넘겨본 경로(`/rss/` 등)의 403은 "그 경로만 거부"로 넘어간다(주간조선은 이것 때문에 처음엔 BLOCKED였다 → 수정).
- 홈 내용으로 사이트 유형을 정한다: `go.kr`·`or.kr` 등은 PUBLIC, 도메인·메타에 news/일보/신문 단서가 있으면 NEWS, 나머지 ETC.
  유형이 기본값을 정한다(NEWS: 60분·제목·링크·발행일만 저장, PUBLIC: 360분·본문·첨부 저장).
- 공개 API 카탈로그에 있는 도메인(DART, 네이버 뉴스, 공공데이터포털)은 크롤링하지 않고 API 소스로 넘긴다. 키가 없으면 큐에 "API 키 필요".

## 2. 입구(허브) 찾기 (DISCOVERY) — 앞 단계에서 찾으면 뒤로 가지 않는다

| 순서 | 방법 | 실제 예 |
| --- | --- | --- |
| ① RSS | 홈 `<link rel="alternate" type="rss">`, 없으면 국내 CMS 관례 경로를 넘겨본다 (`/rss`, `/rss.xml`, `/feed`, `/rss/allArticle.xml`, `/rss/S1N1.xml`, `/rssIndex.html`) | 주간조선·한국경제·지디넷·디지털데일리·블로터·시사저널 |
| ② 사이트맵 | `robots.txt`의 `Sitemap:`을 읽고, 인덱스면 `lastmod`가 최신인 하위 사이트맵 3개만 연다 | 연합뉴스·정책브리핑·EE Times |
| ③ 홈·섹션 링크 | 홈과 "보도자료·공지·뉴스" 같은 메뉴 링크를 열어 기사형 링크를 모은다 | 과기부·산업부·전자신문 |

입구에서 모은 링크는 **같은 사이트 것만** 남긴다. 다른 사이트로 가는 링크가 10곳 이상이고 자기 기사형 링크보다 많으면
"링크 모음(포털) 페이지"로 보고, 실패시키는 대신 **가리키는 언론사들을 대신 등록**한다(뉴스스탠드 → 언론사 50곳, 상한 50).
뉴스스탠드처럼 매체 목록이 인라인 스크립트의 JSON에만 있는 경우도 읽는다.

## 3. 기사 패턴 만들기 (URL 서명)

링크 주소에서 숫자는 `{n}`, 숫자가 섞인 긴 영숫자 ID는 `{id}`, 하이픈으로 이어진 영문 슬러그는 `{slug}`로 바꾼 "서명"을 만들고,
가장 많이 반복되는 서명을 기사 패턴으로 고른다. 섹션 이름만 다른 서명은 `{*}`로 합친다.

```
/news/articleView.html?idxno=50103            → /news/articleView.html?idxno={n}      주간조선·블로터 (ndsoft CMS)
/view/AKR20261015138000530                    → /view/{id}                             연합뉴스
/briefing/pressReleaseView.do?newsId=156748578 → /briefing/pressReleaseView.do?newsId={n}  정책브리핑
/news/economy/12175940 + /news/society/…      → /news/{*}/{n}                          매일경제 (섹션 병합)
/samsung-lays-out-ai-memory-roadmap/          → /{slug}/                               EE Times
/news/articleList.html?sc_section_code=S1N1   → 목록 주소, 제외
/member/login.html                            → 식별자 없음, 제외
```

목록·검색·로그인·태그·인쇄 경로와 이미지·PDF 등은 규칙으로 뺀다. 추적용 파라미터(`utm_*`, `page` 등)는 서명과 정규 주소에서 뺀다.
이 패턴이 이후 "이 링크가 기사인가"를 가르는 기준이다.

## 4. 샘플 품질 검사 (QUALITY)

후보 패턴마다 샘플 기사 5건을 열어 제목·발행일·본문이 뽑히는지 본다. 사이트별 셀렉터 없이 표준 메타를 읽는다.

```
og:type = article
og:title = 주둥이 다치더니 지느러미까지…떠나지 않는 '부캉이', 왜 상처 입었나
article:published_time = 2026-10-18T22:33:53+09:00
article:section = 사회
```

- 메타가 없으면 JSON-LD(NewsArticle), 비표준 발행일 메타(`h:published_time`·`publish_date`·`DC.date.issued` 등, 값이
  `202610160849`처럼 구분자 없는 것도), `<time datetime>`, "등록일 2026.10.15"·"등록 2026-10-16 08:49" 같은 라벨 옆 날짜,
  목록 행에 적힌 날짜 순으로 본다(공공기관 게시판). 사이트 꼬리(`<footer>`)의 "등록·발행일자"(매체 등록일)는 보지 않는다.
- 본문은 trafilatura → `<article>`·본문 컨테이너 → 가장 긴 문단 묶음. 머리말·메뉴·꼬리는 지우되 본문 컨테이너를 품은 것은 남긴다
  (기사 전체를 `<header>` 안에 두는 CMS가 있다). 공공기관은 본문 대신 HWP·PDF 첨부가 있어도 통과.
- **5건 중 4건 이상** 통과하고 최근 30일 안 글이 있어야 등록된다. 아니면 다음 후보 패턴을 검사하고, 모두 실패하면 관리자 큐(`REVIEW`)로.
  - `[부고]`·`[인사]`·`[포토]` 같은 정형 단신은 본문이 한두 줄이라 표본에서 빼고 다음 후보 주소로 채운다(최대 10건까지 열어 봄).
  - 2026-10-18에는 한겨레21(꼬리의 "등록·발행일자 2011년"을 발행일로 읽음 → "30일 안 글 없음")과
    주간한국(최신 글이 부고 단신이거나 본문을 `<header>`와 함께 지움 → "5건 중 2건")이 REVIEW였다. 2026-10-19에 규칙을 고쳐 둘 다 자동 등록된다.

## 5. 설정 저장과 첫 수집

통과한 결과(방식, 허브 목록, 기사 패턴, 제외 섹션, 저장 범위, 셀렉터)를 **설정 버전 v1**로 저장하고 소스를 ACTIVE로 만든다.
첫 수집은 입구에 지금 보이는 최신 기사부터 **실행당 최대 40건**을 가져온다(등록 전 기사는 6-1절 과거 기사 채우기로 따로 요청한다).
언론사는 저작권 때문에 제목·링크·발행일만 저장하고 본문은 두지 않는다. 공공기관·기타는 본문과 첨부 링크까지 저장한다.

## 6. 주기 수집 (CRAWL)

주기마다 허브를 다시 열어 링크를 패턴과 대조하고, **아직 못 본 주소(url_hash)만** 연다. 이미 본 기사는 다시 열지 않는다.
- 허브 하나가 404여도 다른 허브로 계속 간다(PARTIAL). 차단 신호(봇 확인·429·로그인)는 즉시 멈추고 `BLOCKED`.
- 후보 수가 평소의 30% 미만이면 `ANOMALY_DROP`, 2회 연속이면 `BROKEN`(사이트 개편 의심) → 관리자 큐.
- 새 기사가 거의 없는 소스는 주기를 스스로 늘리고(최대 하루 1회), 많으면 기본값까지 줄인다. 사람이 정한 주기는 잠글 수 있다.
- 도메인당 최소 2초 간격을 워커 여러 대가 DB로 공유한다. 식별 가능한 User-Agent를 쓴다.

## 6-1. 과거 기사 채우기 (BACKFILL, 2026-10-19)

평소 수집은 입구에 지금 보이는 기사만 본다(RSS 50건 안팎, 뉴스 사이트맵 이틀 안팎). 등록 전에 나온 기사는 관리자·등록 담당자가
소스 상세의 **과거 기사 채우기**에서 기간을 정해 요청한다(`POST /api/v1/sources/{id}/backfills`, 기본 최근 3개월, 끝 날짜는 오늘까지).
길이 상한은 설정값(`sensing.backfill.max-days`, 기본 366일)이고 **등록 담당자에게만** 적용한다 — 관리자는 10년처럼 길게(1990년부터) 정할 수 있다.
수집 중(ACTIVE)인 사이트 소스만 되고, 소스당 하나씩 진행한다. 어느 사이트가 얼마나 거슬러 갈 수 있는지는 [archive-sitemap-survey.md](archive-sitemap-survey.md).

**기간 묶음, 최근 것부터** — 긴 기간도 쓸모 있는 순서로 채우려고 요청 기간을 **묶음**으로 나눠 가장 최근 묶음부터 과거로 간다.
- 묶음 길이는 기본 2개월(`sensing.backfill.segment-months`)이고, 보관 사이트맵 파일이 한 달·두 달·석 달 단위면 그 단위에 맞춘다
  (동아일보: 두 달 파일 하나 = 묶음 하나, 1~2월·3~4월 …. 하루 단위 파일이면 한 달 묶음). 연도별·5년 단위처럼 더 긴 파일은 기본 묶음으로 나누고
  한 파일을 여러 묶음이 함께 쓴다(한 번 읽고 글의 날짜로 나눠 넣는다). 시작 날짜는 묶음의 첫날로 맞춘다(07-19 → 07-01).
- 묶음마다 상태(대기·진행·완료·실패)와 찾은 주소·저장·이미 있음·기간 밖·실패 수가 `backfill_segment`에 남는다. 소스 상세에는
  "2026-09~10 완료 21,096건 · 2026-07~08 진행 40% (8,400/21,096) · 2026-05~06 대기"처럼 보인다. 끊겼다 다시 시작하면 남은 묶음부터 잇는다.
- **두 달 더**(`POST .../backfills/{id}/extend`, 묶음 하나 = 단위 개월만큼)는 가장 오래된 묶음 앞에 묶음을 더한다. 끝났거나 취소한 채우기는
  다시 연다. 전에 읽은 파일 중 늘어난 기간의 글이 든 것은 다시 읽고, 전에 열어 보니 기간 밖이던 글 중 늘어난 기간에 드는 것(열어 본 발행일을
  남겨 둔다)은 다시 연다.

**묶음마다 주소 찾기** — 앞에서 덮으면 뒤로 가지 않는다.
1. **보관 사이트맵**: `robots.txt`의 `Sitemap:` 줄(사이트맵 소스면 그 허브도)과 색인의 하위 파일을 모두 `backfill_sitemap`에 적어 두고(색인은 한 번만 읽는다),
   묶음에 필요한 파일만 읽는다. `.xml.gz`는 풀어서 읽는다(풀린 크기 50MB까지).
   - 이름에 날짜가 있으면 그 기간이 묶음에 걸칠 때만: `donga-sitemap-202607-202608.xml.gz`(두 달), `weekly-sitemap-2000-2005.xml.gz`(5년),
     `1993.xml`·`2024_1.xml`(연도), `20261019.xml`·`2026/1019.xml`(하루), `?yyyymm=202512`. 동아일보 색인(181개)으로 확인하면 10년 요청이
     묶음 61개가 되고 묶음마다 자기 두 달 파일 하나만 읽는다(2026-09~10 → `202609-202610`, … 1996-09~10 → `199609-199610`).
   - 이름에 날짜가 없고 번호만 다른 파일이 10개 넘게 있으면(`mbn_all_sitemap0~549.xml` 5,291개, 한국일보·KBS·이데일리·매경, 데일리안 `sitemap_www_0~19`)
     번호 순서가 날짜 순서라고 보고 **이분 탐색**한다: 양 끝 파일을 읽어 번호가 커질수록 최근인지 오래된지 알아내고, 읽은 파일 안 글의 날짜 범위로
     이웃 파일의 범위를 가둬, 묶음에 걸칠 수 있는 파일들의 가운데를 읽는다. 550개 중 두 달 묶음 하나에 파일 열두세 개 + 탐색 열 개 남짓이다.
   - 나머지 이름에 날짜가 없는 파일(korea.kr `sitemap_policy.xml` 같은 종류별 파일, 뉴스 사이트맵)은 색인의 `lastmod`가 묶음 시작 이후일 때만,
     채우기 하나에 60개까지 읽는다(`SENSING_BACKFILL_MAX_SITEMAPS`).
   - 글의 날짜는 **주소 안 날짜**(`/20260915/`, `/2026/09/15/`) → `news:publication_date` → 파일 이름 기간 안으로 자른 `lastmod` 순서로 본다.
     `lastmod`는 나중에 고친 날이 섞이므로(1996 파일에 2024 `lastmod`) "그보다 이른 글"이라는 뜻으로만 쓰고, 상세에서 본 발행일로 다시 확인해
     맞는 묶음으로 옮긴다.
   - 묶음을 덮었다고 보는 것: 이름에 날짜가 있는 파일이 묶음에 걸치거나, 날짜 없는 파일의 가장 이른 글이 묶음 시작(+3일)까지 닿았을 때.
2. **목록 페이지 역순**: 사이트맵이 묶음을 덮지 못하면(뉴스 사이트맵·RSS만 있는 22곳, 사이트맵 없는 4곳) 목록 페이지(HTML 허브. 피드·사이트맵
   소스는 탐색 때 본 섹션 8곳)를 쪽 번호로 거꾸로 넘긴다. 쪽 번호는 목록의 쪽 링크에서 찾는다(`?page=2`처럼 숫자만 다른 매개변수, `/page/2/`,
   `fn_egov_link_page(2)` 같은 스크립트 + 폼의 hidden `pageIndex`). 쪽은 **묶음 사이에 이어서** 넘긴다 — 한 묶음은 쪽 맨 아래 글이 묶음 시작보다
   이르면 끝나고, 다음 묶음은 그다음 쪽부터 간다. 앞 쪽에 없던 글(모든 쪽에 고정된 공지는 빠진다)이 모두 요청 기간 시작보다 이르면 그 허브는 끝이다.
   목록에 날짜가 없으면 그 쪽 글을 열어 본 발행일(이미 있는 글은 DB의 발행일)로 정한다. 새 글이 없는 쪽이 나오면 목록 끝으로 본다. 허브 하나에 300쪽까지.

**판정·저장은 평소 수집과 같다.** 같은 기사 패턴(`article_pattern`, 기사 종류 목록이 있으면 켜진 종류), 같은 추출(설정 셀렉터·날짜 형식),
같은 저장 범위(언론사는 제목·링크·발행일만, 본문 미저장), 같은 키워드 감시 대조. 이미 있는 문서(url_hash)는 열지 않고 "이미 있음"으로 센다.
열어 본 발행일이 요청 기간 밖이거나 없으면 저장하지 않는다("기간 밖"). 새 문서의 수집 시각(`collected_at`)은 **발행 시각**으로 둔다 —
다이제스트("지난번 이후 새로 들어온 문서")·문서 화면의 오늘·3일·7일·색인과 요약 순서처럼 수집 시각을 "새로 들어온 것"으로 쓰는 곳에
석 달 전 기사가 새 기사처럼 끼지 않게 하려는 것이다(채운 시각은 `backfill_url.done_at`에 남는다).

**저속·저우선**
- 작업 하나(`crawl_job` BACKFILL) = 요청 100건(`SENSING_BACKFILL_CHUNK`, 사이트맵·목록·기사·robots 포함). 작업마다 진행 위치(묶음 상태, 읽은 사이트맵 파일,
  목록 쪽 번호, 찾은 주소별 상태)를 남기고 끝난다. 다음 작업은 큐가 빈 워커가 색인·요약 한 묶음 뒤에 넣는다. 워커가 죽어도 남은 주소·묶음부터 이어 한다.
- 다른 작업이 하나라도 대기하면 작업을 넣지 않고, 큐에서도 맨 뒤에 집는다. 작업 도중에도 기사 한 건마다 확인해 평소 수집·등록이 대기하거나
  이 소스의 주기 수집 차례가 오면 멈춘다. 스케줄러는 채우기가 자리를 잡은 소스의 차례를 미루지 않고(워커가 보고 멈추면 다음 틱에 CRAWL),
  대기 중인 채우기 작업은 거두고 CRAWL을 넣는다. 관리자의 "지금 수집"도 같다. "다시 탐색"은 채우기를 취소한 뒤에 한다.
- 도메인 간격 2초·robots는 평소와 같다. 차단 신호(봇 확인·429·로그인)는 우회하지 않고 즉시 멈추고 소스를 `BLOCKED`로 둔다(그 묶음은 실패).
- 취소하면 실행 중인 작업은 다음 기사 전에 멈추고, 저장한 문서는 그대로 둔다. 진행 중이던 묶음은 대기로 돌아가 "두 달 더"로 다시 열면 거기서 잇는다.
- 소스 상세 표에 채우기마다 찾은 주소·새로 저장·이미 있음·기간 밖·실패·남은 수와 묶음 칩(최근 8개, 나머지는 접힘), 이번 묶음 남은 시간이 보이고
  진행 중이면 10초마다 갱신된다.

**속도 (사이트 하나 기준)** — 기사 한 건 ≈ 도메인 간격 2초 + 응답 0.5초. 묶음 하나는 그 묶음의 기사 수 × 2~2.5초다.

| 사이트 | 묶음(2개월) 하나 | 석 달 | 10년(묶음 60개) |
| --- | --- | --- | --- |
| 동아일보 전체 (두 달 파일 = `.xml.gz` 180KB, 풀면 3MB, 주소 21,096개) | 약 12시간(2초) ~ 15시간(2.5초) | 약 18~22시간 | 약 29~37일 |
| 동아일보, 지금 설정(사회면 패턴만, 두 달 5,679건) | 약 3~4시간 | 약 5~6시간 | 약 8~10일 |
| 공공기관 게시판 (하루 몇 건) | 몇십 분 | 1시간 안팎 | 하루 안팎 (목록이 그만큼 남아 있다면) |

위는 워커가 평소 수집 틈에 이 사이트만 채울 때의 하한이다(평소 수집에 양보하는 시간은 더 걸린다). 사이트맵 파일 읽기는 묶음당 한두 건이라 무시할 만하다.
도메인 간격은 사이트마다 따로라 워커를 늘리면 여러 사이트를 함께 채우지만, 한 사이트는 빨라지지 않는다.
2026-10-19 실측: 동아일보 robots·색인·7~8월 파일 하나를 4건 요청으로 읽어 2개 파일(9~10월, 7~8월)을 골랐고, 묶음 계산은 색인 1건으로 확인했다.

**한계**
- 보관 사이트맵도 넘길 목록도 없는 곳(피드만 있는 소스, 스크립트로 그리거나 POST로만 넘기는 게시판)의 묶음은 실패로 남기고 이유를 메시지에 쓴다.
  "최근 글만" 사이트 22곳(연합뉴스·한겨레 등)은 목록 역순이 되는지, 몇 쪽까지 열리는지 사이트마다 다르다.
- 번호 묶음의 이분 탐색은 번호가 날짜 순서라고 가정한다. 글 날짜(주소 안 날짜·발행일)가 없고 `lastmod`도 모두 최근으로 다시 쓰인 파일이면 범위를 가두지
  못해 목록 페이지로 넘어간다.
- 날짜를 넣어 여는 검색 화면은 쓰지 않는다(동아일보처럼 `/search`를 robots가 막는 곳이 많다).
- 기사 패턴이 좁으면(위 동아일보) 채우기도 좁다 — 다시 탐색이나 사이트 하나에 기사 종류 여러 개(작업 중)로 넓힌다.
- 요약·분류(LLM)는 큐가 빌 때 10건씩이고 최근 수집 문서가 먼저라, 채운 기사 수만 건에는 며칠에 걸쳐 붙는다.

**이슈 묶기**: 이슈는 문서 시각(발행일) 앞뒤 72시간 창으로만 비교하고, 창보다 오래된 문서는 그 시점 근처의 닫힌 이슈와만 비교한다
(`issues.doc_time`, 아래 "인덱싱과 이슈 묶기"). 그래서 석 달 전 같은 제목 기사가 지금 이슈에 붙지 않는다(테스트로 확인).

**저작권 원칙**은 평소 수집과 같다. 언론 기사는 제목·링크·발행일만 저장하고 본문은 저장·색인하지 않는다(키워드 대조에만 메모리에서 본다).
`robots.txt`가 연 경로만, 사이트가 공개한 사이트맵·목록에 있는 글만 연다. 여러 언론사의 긴 기간 원문이 필요하면 빅카인즈 같은 뉴스 DB 계약이 맞다.

## 입구 파일이 보여 주는 범위와 과거 기사 (2026-10-19 실측)

RSS와 사이트맵은 둘 다 사이트가 공개한 **글 주소 목록(XML)** 이다. 브라우저로 주소를 여는 것과 같은 요청 한 번으로 받고,
정해진 칸(RSS `<item><link>`, 사이트맵 `<url><loc>`)에서 주소만 뽑는다. 검색이나 LLM은 쓰지 않는다.

| | RSS | 사이트맵 |
| --- | --- | --- |
| 만든 목적 | 구독자에게 새 글 알림 | 검색엔진에 글 목록 알림 |
| 들어 있는 것 | 최신 20~50건 | 뉴스 사이트맵은 최근 이틀, 전체·보관 사이트맵은 수천~수십만 건 |
| 글마다 | 제목·주소·발행 시각·요약 | 주소·수정일(뉴스 사이트맵은 제목·발행 시각도) |
| 주소 찾는 곳 | 홈의 `<link rel="alternate">`, CMS 관례 경로 | `robots.txt`의 `Sitemap:` 줄 |

수집 중인 사이트 52곳(ACTIVE SITE)의 방식: **RSS 28 · 사이트맵 17 · 페이지 링크 7**. XML이 없는 곳은 주로 시청·도청 게시판이다.
XML도 링크도 못 쓰는 곳은 봇 확인 화면(우회하지 않음)과 자바스크립트로 그리는 화면(동적 수집, M4)이다.

**RSS는 최신 몇십 건뿐이라 주기가 덮는 시간보다 짧아야 한다.** 동아일보 실측:

| RSS | 건수 | 덮는 시간 |
| --- | --- | --- |
| 전체 `rss.donga.com/total.xml` | 50 | 약 3시간 (12:12~15:18) |
| 경제 | 50 | 약 11시간 |
| 정치 | 50 | 약 2일 |

동아일보는 전체 + 분야별 RSS 5개를 허브로 두고 60분마다 연다. 매번 앞뒤가 겹쳐 빈틈이 없다(한 실행에 44건 중 2~27건이 새 기사).
주기 자동 조정(6절)이 이 겹침을 유지한다.

**사이트맵은 종류가 셋이다.**
- 뉴스 사이트맵: 최근 이틀(동아일보 `donga-newsmap.xml` 332건). 평소 수집에 쓰기 좋다.
- 보관 사이트맵: 기간별 파일. 동아일보는 `image.donga.com/sitemap/donga-sitemap.xml` 색인 아래 1996-09부터 두 달 단위 `.xml.gz` 181개.
- 종류별 사이트맵: korea.kr은 `sitemap_brief`(보도자료 6,986) · `sitemap_policy`(정책뉴스 3,445) · `sitemap_actually`(사실은 이렇습니다 2,012) ·
  `sitemap_briefing`(대통령·국무회의 1,990) · `sitemap_speech`(연설문 881) 등으로 나뉜다.

**정책브리핑 RSS는 2026-07-01 중단됐다.** 홈 공지 "정책브리핑 RSS 서비스 제공 중단 안내"의 사유는 "콘텐츠 저작권 등 권리 보호에 따른
제공방식 변경"이다. 사이트맵은 공개돼 있고 `robots.txt`도 전부 허용하므로 수집은 사이트맵으로 계속한다. 다만 지금 korea.kr은 PUBLIC이라
본문까지 저장하므로, 공공누리 표시가 있는 글만 본문을 두고 나머지(기고 등)는 제목·링크만 둘지 법무 확인이 필요하다.

**지금 한계 두 가지.**
1. 사이트당 기사 패턴이 하나다. korea.kr은 보도자료(`pressReleaseView`) 패턴 하나만 골라 문서 80건이 전부 보도자료다. 메뉴 32개는 찾았지만
   정책뉴스·브리핑·연설문은 주소 모양이 달라 기사로 인정되지 않는다. 같은 도메인은 중복 등록도 막혀 있다.
   → 사이트 하나에 기사 종류 여러 개(종류별 품질 검사, 비기사 종류 기본 꺼짐, 실행 상한 종류별 분배, 특정 목록 주소로 등록하면 그 종류만,
   이미 있는 사이트에 다른 목록 주소를 넣으면 종류 추가)를 작업 중이다(10-19).
2. **과거 기사가 없었다.** 등록한 뒤 입구에 보이는 기사부터 모은다. 현업은 이전 기사도 필요하다(10-19 확인, 필수).
   → 과거 기사 채우기(6-1절)를 만들었다: 사이트·기간(기본 최근 3개월)을 정하면 ① 보관 사이트맵 → ② 목록 페이지를 쪽 번호로
   거꾸로 넘기기 순서로 주소를 모으고, 평소 수집과 같은 판정·추출·저장·감시 대조를 거친다. 평소 수집이 쉬는 틈에만 돌고 끊어 이어 한다.
   도메인당 2초 간격이면 사이트 하나에 시간당 약 1,400~1,800건이라, 하루 수백 건 나오는 언론사 석 달 치는 하루 가까이 걸린다.
   여러 언론사의 긴 기간이 한꺼번에 필요하면 한국언론진흥재단 빅카인즈 같은 뉴스 DB 계약이 더 빠르다(저작권도 계약으로 정리).

## 7. LLM이 들어가는 자리 (선택)

- **등록 시 레시피**(`SENSING_LLM_PROVIDER` 설정 시): 홈과 샘플 페이지를 보여 주고 허브·기사 패턴·제목/날짜/본문 셀렉터를 JSON으로 받는다.
  규칙이 못 잡는 사이트용 보조이며, LLM 답도 위 4단계 품질 검사를 똑같이 통과해야 저장된다. LLM 장애는 규칙으로 넘어간다.
- **수집 뒤 요약·분류**: 큐가 비었을 때 문서 10건씩 묶어 한 줄 요약과 토픽(정책·규제, 입찰·공고, 자사, 경쟁사 …)을 붙인다. 언론 기사는 제목만 분류하고 요약을 저장하지 않는다.
- 규칙을 기본으로 둔 이유: 사이트 수백 곳을 매시간 도는 비용과, 같은 사이트에서 같은 답이 나와야 하는 재현성.

## 수집 뒤: 인덱싱과 이슈 묶기

큐에 작업이 없을 때 워커는 LLM과 상관없이 아직 색인하지 않은 문서를 200건씩 집어(`indexed_at IS NULL`, 본문이 바뀌면 다시 비워진다)
제목을 0번 조각, 저장한 본문을 800자 안팎 조각(최대 20개)으로 나눈다. 언론 기사는 본문을 저장하지 않으므로 제목 한 조각뿐이다.
조각마다 한국어 낱말을 미리 뽑아(Kiwi 형태소 분석: 명사·고유명사·외국어·"3분기" 같은 숫자+단위, 붙여 쓴 복합어도 함께. Kiwi가 없으면
조사를 떼는 정규식) `chunk.tokens`에 넣고, 문서 화면의 검색어는 이 낱말들을 접두 일치로 찾는다("반도체가" → "반도체"). 같은 트랜잭션에서
문서마다 **이슈**를 정한다: 제목 낱말([단독]·(종합)·연재명·흔한 낱말은 뺀다)이 최근 72시간 이슈의 핵심 낱말(소속 기사 제목에 많이 나온
15개)과 충분히 겹치면(겹침 계수 0.4 이상, 겹친 낱말 2개 이상, 2개뿐이면 0.66 이상) 그 이슈에 붙이고, 아니면 새 이슈를 만든다.
그래서 "할리스 개인정보 유출"을 쓴 언론사 10곳의 기사 11건이 이슈 하나("언론사 10곳 · 기사 11건")로 보인다. 72시간 동안 새 기사가 없는
이슈는 닫혀 더는 비교하지 않는다. 72시간은 수집 시각이 아니라 문서의 발행 시각 기준이라, 과거 기사 채우기로 들어온 석 달 전 기사는
그 무렵(앞뒤 72시간)의 이슈와만 비교된다. 임베딩(의미 검색)은 아직 없고 `chunk.embedding`은 비어 있다 — 챗봇(M5) 단계에서 채운다.

## 수집 뒤: 키워드 감시 대조

키워드 감시는 사이트가 아니라 "이 말이 나온 기사"를 모은다. 워커는 기사(그리고 DART 공시 같은 API 문서)를 새로 저장하거나 고칠 때마다
제외되지 않은 모든 감시의 키워드와 대조한다(`watchmatch`: 대소문자·공백 차이 무시, 띄어쓰기가 다르면 다른 말, 제목·본문 어디든, 제외어가
제목에 있으면 뺀다, 감시당 처음 걸린 검색어 하나). 걸리면 `document_watch`(감시·검색어)에 남고, 회사 감시면 그 회사에도 연결된다.
그래서 감시의 커버리지는 **등록된 언론사의 수**가 정한다 — 감시를 만들었다고 새로 긁는 곳이 생기지는 않는다.

이것이 기본(수집 기사 대조 모드, 설정 `"naver": false`)이다. 감시를 만들면 바로 `ACTIVE`가 되지만 스스로 수집할 것이 없어 `next_run_at`이
비어 있고, 스케줄러는 이런 소스에 작업을 넣지 않는다(관리자가 실행을 눌러도 워커가 키를 찾지 않고 바로 끝낸다). 감시를 만들기 전에 쌓인
기사는 `python -m sensing_worker.backfill_watch --days 30`으로 한 번 대조한다. 네이버 뉴스 검색 API 키가 있으면(2026-07-31부터 신규 발급이
막혀 보통은 없다) 감시에 네이버 검색이 함께 붙어(`"naver": true`) 60분(회사 감시 360분)마다 검색어별 최신 기사 제목·링크를 받아 오고,
대조는 그와 별개로 계속된다.
