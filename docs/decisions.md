# 설계 결정 기록

| 결정 | 이유 |
| --- | --- |
| 등록 단위는 도메인, 사용자는 URL만 입력 | 사용자 부담 최소화. 판단이 필요한 건 관리자 큐로 보낸다 |
| Java(Spring Boot)가 본체, Python은 작업자 | 관리자 화면·권한·연동 확장은 Java가 유리, 크롤링·문서 추출 생태계는 Python이 유리 |
| DB 작업 큐 (`FOR UPDATE SKIP LOCKED`) | 저사양 단일 서버에서 구성 요소를 줄이기 위해 메시지 브로커를 쓰지 않는다 |
| 소스당 열린 작업 1개 (부분 유니크 인덱스) | 스케줄 실행과 수동 실행이 겹쳐도 같은 사이트를 두 번 긁지 않는다 |
| 작업 임대(lease) + 하트비트 | 워커가 죽어도 스케줄러가 작업을 회수한다 |
| 설정은 버전으로 쌓고 포인터로 전환 | 사이트 개편 대응 중 실수해도 즉시 롤백할 수 있다 |
| 원본 저장과 인덱싱 분리 | 임베딩 실패가 수집 실패가 되지 않고, 모델 교체 시 재크롤링이 필요 없다 |
| 문서는 본문 해시가 바뀔 때만 새 버전 | 수정·삭제된 기사를 추적하면서 저장 공간을 아끼기 위해 |
| 대화 기록은 DB 저장 | 다른 PC에서 이어보기, 등록 요청 추적, 피드백·감사가 필요하다. 하루 약 60MB(1,000명 가정)로 부담이 작다 |
| 차단·로그인·CAPTCHA는 우회하지 않음 | 이용약관·법적 리스크. 실패 사유로 분류하고 관리자에게 넘긴다 |
| 사용자가 넣은 주소는 내부망 여부를 두 번 검사 | 백엔드는 주소 형식으로, 워커는 요청 직전에 DNS 결과로 막는다 (프록시 환경은 형식 검사만) |
| 등록 시 LLM이 수집 레시피를 쓰되, 제공자는 교체 가능하고 출력은 우리 쪽에서 검증 | Claude일 수도 사내 반입 오픈소스 모델일 수도 있다. 스키마·셀렉터·샘플 품질 검사를 통과한 것만 저장하고, LLM 장애는 휴리스틱으로 넘긴다 |
| 언론 보도·공시는 공개 API 우선, 크롤링은 API가 없는 게시판에 | 약관이 허용하고 키워드로 바로 받으며 차단이 없다. 언론 본문을 저장하지 않는 저작권 원칙과도 맞는다 (2026-10-16, 현업 요청서 반영) |
| API 키는 사람이 발급, 시스템은 검증·암호화 보관·쿼터·만료 감시만 | 자동 가입·약관 동의 대행은 봇 가입과 같아 컴플라이언스 위반. 필요한 API는 다섯 곳 안팎이라 수동 발급 부담이 작다 |
| 언론 기사는 요약도 저장하지 않는다 (제목만 분류) | 제목·링크만 저장하는 저작권 원칙을 요약으로 우회하지 않기 위해. 요약은 본문을 저장하는 공공기관·기타 문서에만 만든다 (2026-10-16) |
| 요약·분류(보강)는 수집과 별도 단계, 큐가 비었을 때 묶음으로 | LLM 장애·검증 실패가 수집 실패가 되지 않고, 문서 10건을 한 호출에 묶어 비용을 줄인다. 실패는 FAILED로 남겨 24시간 뒤 재시도 |
| 키워드 감시와 일간 다이제스트를 챗봇보다 먼저 | 대외협력·커뮤니케이션 업무는 물어보기(pull)보다 받아 보기(push)다. 챗봇은 그 위의 보조 |
| 키워드 감시는 네이버 검색 API가 아니라 직접 수집한 언론사 기사에 대한 키워드 대조를 주 경로로 한다 | 2026-10-19 확인: 네이버 검색 API 신규 발급이 막혔고 이관된 API HUB 약관이 결과 저장·가공(요약·분류) 용도와 맞지 않을 가능성이 크다. 커버리지는 등록 언론사를 늘려(뉴스스탠드 확장 등) 넓히고, 정식 뉴스 데이터가 필요하면 빅카인즈(한국언론진흥재단) 같은 계약 경로를 검토한다 |
| 회사 계정 로그인 수집은 현업 서면 합의 뒤에만 | 정당한 구독 소스는 허용할 수 있으나, CAPTCHA·IP 우회와 선을 긋는 범위를 문서로 남겨야 한다 |
| 챗봇은 도구 호출만 하고 등록·검증·수집은 결정적 코드가 한다 | 챗봇이 상태를 거짓으로 답할 여지를 없앤다. 화면과 챗봇이 같은 등록 함수를 쓴다 |
| API 키·계정은 대화 본문에 남기지 않고 자격 증명 테이블에 암호화 저장 | 대화 기록이 DB에 영구 보관되기 때문 |
| 케이던시아 병행에 맞춰 고객·엔진은 유지하고 데이터 소스를 공급사 리스크 쪽으로 넓힌다 (M3 회사 레이어) | 수집 엔진의 8할이 그대로 쓰이고, 바뀌는 건 묶는 단위(문서→회사)와 소스(국세청·조달청·DART 재무)·출구(회사별 다이제스트, 케이던시아 이벤트)다. 동적 수집·첨부보다 "어느 회사에 무슨 일"이 먼저 (2026-10-16) |
| 문서→회사 연결은 회사 감시의 검색어(WATCH)와 보강 태그의 **정확 일치**(TAG)만, 부분 일치·유사도 매칭은 하지 않는다 | 거래처 신호는 사람이 조치하는 입력이라 엉뚱한 회사에 붙은 오탐이 누락보다 해롭다. 별칭을 넉넉히 넣는 쪽으로 푼다 (2026-10-16, M3-1) |
| 회사 단위 외부 점검은 회사마다 소스를 만들지 않고 시스템 소스 하나(`kind CHECK`)가 모든 회사를 돈다 | 국세청 상태조회는 100건씩 묶어 부르는 API라 회사 수와 무관하게 하루 몇 번의 호출이면 되고, 키 대기·실패·재점검을 기존 소스 운영 규칙(관리자 큐 API_KEY, REVIEW)으로 그대로 다룰 수 있다. 급감 감지는 점검에 적용하지 않는다 (2026-10-16, M3-1) |
| 회사 신호는 (회사, 종류, fingerprint)로 유일하다 | 폐업처럼 바뀌지 않는 상태를 매일 확인해도 신호는 한 번만 남아야 다이제스트가 조용하다. fingerprint는 상태 코드+폐업일(BIZ_STATUS), url_hash(NEWS), 접수번호(DISCLOSURE), 제재 시작일+기관(DEBARMENT) (2026-10-16, M3-1·M3-2) |
| 점검 소스는 제공자가 아니라 **점검 종류**(config `check`)로 커넥터를 고르고, 종류마다 시스템 소스 하나다 | 공공데이터포털 키 하나가 국세청·조달청을, DART 키 하나가 고유번호 매핑·회사별 공시를 덮는다. 종류별로 소스를 나눠야 주기(매일·주 1회·6시간)와 키 대기·실패를 따로 다룰 수 있다 (2026-10-16, M3-2) |
| DART 고유번호는 이름 정규화 뒤 **정확 일치가 하나일 때만** 자동으로 채우고, 여럿이면 상장사 하나일 때만, 그래도 여럿이면 비워 둔다 | 잘못 붙은 고유번호는 엉뚱한 회사의 공시를 신호로 만든다. 모호한 회사는 로그로 알리고 사람이 수정 API로 넣는다 (2026-10-16, M3-2) |
| 케이던시아 연동은 실제 API 없이 **가짜 케이던시아를 우리 백엔드 안에 두고** 연동 코드는 그것을 외부 시스템처럼 HTTP로 부른다 | SDS API 스펙을 기다리면 연동 형태(마스터 동기화·이벤트 전달·실행 기록·화면)를 현업에 보여 줄 수 없다. 목업을 같은 프로세스에 두면 서버 하나로 데모가 되고, 실제가 나오면 `base-url`·키·필드 매핑만 바꾼다. 매칭은 `external_id` → 사업자번호 순이고 태그는 외부가 정한다 (2026-10-16, M3) |
| 조달청 부정당업자는 **사업자번호별 조회**로 시작한다 (전체 목록 기간 조회는 설정으로) | 공공데이터포털에 확인된 조회 모드가 `inqryDiv=1`(bizno)뿐이고 응답 항목명도 공개돼 있지 않다. 추측하지 않고 항목명·조회구분을 config(`fields`, `mode`, `period_inqry_div`)로 두어 활용신청 뒤 미리보기로 확인한 값을 넣는다 (2026-10-16, M3-2) |
| 모음 페이지는 실패시키지 않고 가리키는 언론사를 대신 등록 | 뉴스스탠드처럼 다른 언론사 링크만 모아 둔 페이지는 "여기 나오는 매체를 다 보고 싶다"는 뜻이지 그 페이지를 긁어 달라는 뜻이 아니다. 관리자 큐에 보내 사람이 수십 곳을 다시 넣게 하는 대신, 외부 언론사 도메인 10곳 이상이고 외부 링크가 자기 기사형 링크보다 많을 때만 백엔드 등록과 같은 규칙(중복·내부망·요청자)으로 묶음 `portal:<소스 id>`에 등록한다. 모음 페이지 자체는 `EXCLUDED/PORTAL_EXPANDED`로 남겨 다시 등록해도 중복으로 막히지 않는다 (2026-10-18, M3) |
| 전문 검색은 PostgreSQL 한국어 검색 설정 대신 **워커가 미리 뽑은 낱말을 `to_tsvector('simple', ...)`** 로 넣는다 | PostgreSQL에는 한국어 사전이 없고 확장(mecab-ko 등)은 사내 DB에 설치하기 어렵다. 형태소 분석(Kiwi)은 파이썬 워커에서 하고 DB는 이미 있는 `chunk.tokens` GIN 인덱스로 찾기만 한다. Java에는 분석기가 없으므로 질의는 띄어쓰기 단위로 나눠 같은 조사 목록으로 끝을 떼고 접두 일치(`:*`)로 찾으며, 색인 쪽에 붙여 쓴 복합어(영업이익, LG에너지솔루션)와 정규식 낱말을 함께 넣어 질의와 맞춘다. 분석기는 `chunk.index_version`(`fts-kiwi-v1`/`fts-regex-v1`)에 남겨 나중에 다시 색인할 문서를 가린다. 검색은 낱말마다 문서의 어느 조각에든 있으면 되고(제목+본문 조합), 색인 전 문서만 예전 부분 일치로 찾는다 (2026-10-19, M5) |
| 이슈(중복 보도) 묶기는 임베딩 없이 **72시간 창 안에서 제목 낱말 겹침**으로, 결정적으로 | 수집 문서 대부분이 본문 없는 언론 기사라 제목이 유일한 공통 재료이고, 같은 사건 기사는 핵심 낱말(인명·기관·사건어)을 공유한다. 새 기사의 제목 낱말과 이슈 서명(소속 기사 제목 낱말 빈도 상위 15개)의 겹침 계수(서명이 커져도 불리하지 않음) ≥ 0.4, 겹친 낱말 ≥ 2, 2개만 겹치면 ≥ 0.66. 운영 DB 제목 2,998건(53개 언론사, 읽기만)으로 보정: 0.5·2개 조건은 2개만 겹친 결합 다수가 '서울·축제', 'AI·반도체' 같은 우연이었고, 0.40~0.45 구간에서 거절되던 결합은 대부분 같은 사건이었다 → 2곳 이상 이슈 287개·3곳 이상 122개·5곳 이상 47개. 흔한 낱말(단독·속보·정부·대통령·AI 등)과 꼬리표([단독]·(종합)·연재명·'-섹션ㅣ매체')는 뺀다. 대표 제목은 서명과 가장 많이 겹치는 기사(첫 보도는 [단독]처럼 좁은 각도가 많다). 한계: 한 사건의 다른 국면(추미애 발언 → 사과 → 빨대 배송)은 별개 이슈로 나뉜다. 임베딩은 챗봇 단계에서 더한다 (2026-10-19, M5) |
